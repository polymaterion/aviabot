# ✈️ Авиабилеты в Туркменистан (@aviastan)

Telegram-бот для поиска авиабилетов по направлениям, связанным с
Туркменистаном, с использованием Travelpayouts Data API, и для
отслеживания цен на подходящие варианты.

Бот не продаёт билеты сам — при покупке пользователь переходит по
партнёрской ссылке Travelpayouts на страницу продавца.

## Стек

Python 3.13, aiogram 3, PostgreSQL, SQLAlchemy 2 (async), Alembic,
APScheduler, Pydantic Settings, HTTPX, Docker Compose.

## Быстрый старт

1. Скопируйте `.env.example` в `.env` и заполните секреты:

   ```bash
   cp .env.example .env
   ```

   Обязательно укажите:
   - `BOT_TOKEN` — токен вашего бота от @BotFather
   - `TRAVELPOUTS_TOKEN` — API-токен Travelpayouts
   - `TRAVELPOUTS_MARKER` — ваш партнёрский marker/affiliate ID

   `DATABASE_URL` уже настроен на сервис `postgres` из docker-compose —
   менять не нужно, если вы не меняете имена сервисов.

2. Запустите через Docker Compose:

   ```bash
   docker compose up --build
   ```

   При старте контейнера `bot` автоматически применяются миграции Alembic
   (`alembic upgrade head`), создающие всю схему БД в поднятом Postgres.

3. Откройте бота в Telegram и отправьте `/start`.

## Структура проекта

```
app/
├── bot/
│   ├── handlers/     # хендлеры сообщений и callback-кнопок
│   ├── keyboards/     # inline-клавиатуры, карусель, рендер карточек
│   ├── screen/         # менеджер единого фото-экрана (карусели билетов/подписок)
│   ├── states/          # FSM-состояния
│   └── texts/             # все тексты бота (для локализации)
├── services/       # бизнес-логика (поиск, подписки, города, даты, аффилиат)
├── providers/       # абстракция FlightProvider + реализация Travelpayouts
├── database/        # модели SQLAlchemy, репозитории, Alembic-миграции
├── scheduler/        # периодический мониторинг цен (APScheduler)
├── config/           # Pydantic Settings (.env)
├── assets/            # логотип для фото-экранов
└── data/              # cities.json, airlines.json — редактируются без кода
```

## Редактирование городов и авиакомпаний

- `app/data/cities.json` — единый список городов (полный список для ручного
  ввода/поиска). Каждый город размечен полями:
  - `category`: `turkmenistan` (города Туркменистана), `turkmenistan_airlines_destination`
    (зарубежные направления Turkmenistan Airlines), `popular_transit` (популярные
    транзитные города — Россия, Узбекистан и т.п.);
  - `show_in_buttons`: показывать ли город кнопкой в быстром выборе на шагах
    «Откуда»/«Куда» (остальные доступны только через ручной ввод).
- `app/data/airlines.json` — код IATA авиакомпании → полное имя + флаг страны,
  используется в карточке билета.

Оба файла можно редактировать без изменения кода бота.

## Локализация

Все тексты бота вынесены в `app/bot/texts/ru.py`. Чтобы добавить новый
язык, создайте аналогичный файл (например `tk.py` или `en.py`) с тем же
набором констант и подключите выбор языка в `app/bot/handlers/settings.py`
и `app/bot/keyboards/settings.py` (`SUPPORTED_LANGUAGES`).

## Миграции БД

Применить миграции вручную (например, локально без Docker):

```bash
pip install -r requirements.txt
alembic upgrade head
```

Создать новую миграцию после изменения моделей:

```bash
alembic revision --autogenerate -m "описание изменения"
```

## Мониторинг и группировка запросов

Раз в `MONITORING_INTERVAL_MINUTES` минут (по умолчанию 15) фоновая задача:

1. собирает все активные подписки;
2. группирует их по нормализованному ключу поиска (маршрут, даты, тип
   рейса — без учёта индивидуального `max_price`);
3. выполняет **один** запрос к Travelpayouts на каждую уникальную группу;
4. применяет к результатам индивидуальные фильтры каждой подписки и
   решает, нужно ли отправить уведомление (защита от повторных
   уведомлений при неизменной цене — см. `NotificationService`).

## Карточка билета

Формат:

```
🇦🇪 Flydubai

Ашхабад — Москва (внуково)

вылет 21 сентября в 05:15
прилёт в 15:00

🔁 С пересадкой

💰 46150 RUB
```

Строка «🔁 С пересадкой» показывается только если рейс не прямой —
убирается полностью для прямых рейсов.

Названия городов и аэропортов резолвятся через `app/services/airport_service.py`
и `app/data/airports.json` — отдельный справочник, покрывающий и групповые
городские IATA-коды (`MOW` → Москва), и коды конкретных аэропортов
(`SVO`/`DME`/`VKO` → Москва (шереметьево)/(домодедово)/(внуково), `SHJ` →
Шарджа). Это гарантирует, что ни один код, который реально возвращает
Travelpayouts в полях `origin`/`destination`/`origin_airport`/
`destination_airport`, не остаётся непереведённым голым кодом. Если
встретится код, которого нет в справочнике, добавьте его в
`app/data/airports.json` — код не привязан к бизнес-логике.

Ключевые детали по данным Aviasales Data API:

- Эндпоинт `/aviasales/v3/prices_for_dates` не отдаёт `arrival_at` вообще
  — время прибытия вычисляется как `departure_at + duration` (или
  `duration_to` для round-trip, где `duration` — суммарная длительность
  обеих ног, а `duration_to`/`duration_back` — длительность каждой ноги).
- Эндпоинт не даёт город пересадки и время ожидания между рейсами —
  только число пересадок (`transfers`), поэтому карточка показывает
  «🔁 С пересадкой» одной строкой вместо выдуманной детализации, которой
  у провайдера нет.
- Параметр `one_way` передаётся в запрос автоматически (`true` для
  поиска в одну сторону, `false` для туда-обратно) — без этого
  Travelpayouts группирует результаты по дате и возвращает только один
  билет вместо нескольких вариантов для листания.

## Клавиатура выбора города

Раскладка кнопок (реализовано в `app/bot/keyboards/cities.py`):
3 ряда по 2 города, 4-й ряд — 1 город и кнопка «🌎 Другой город» рядом с
ним, 5-й ряд — «❌ Отмена». Всего 7 городов кнопками, помеченных
`show_in_buttons: true` в `app/data/cities.json`.

Если пользователь уже выбрал город (например, как «Откуда»), этот город
исключается из списка при выборе «Куда» — вместо него автоматически
подставляется следующий город из резервного пула (`show_in_buttons: false`
в `cities.json`), чтобы кнопок всегда было ровно 7, а не 6.

## Уведомления о снижении цены

Уведомление о снижении цены отправляется, только если цена упала больше
чем на пороговое значение — раздельно для каждой валюты (300 ₽ для RUB,
5 для USD/EUR по умолчанию, т.к. одинаковое абсолютное число в разных
валютах означает разную по значимости величину изменения). Пороги
настраиваются в `.env` (`PRICE_DROP_NOTIFICATION_THRESHOLDS`,
`PRICE_DROP_NOTIFICATION_DEFAULT_THRESHOLD`) без изменения кода, и нигде
не упоминаются в текстах бота. Первое появление подходящего билета и его
повторное появление после пропажи уведомляются всегда, независимо от
порога — иначе пользователь мог бы вовсе не узнать о найденном билете.

## Единый фото-экран на всех шагах бота

Все экраны бота — главное меню, выбор города, даты, фильтры, результаты
поиска, подписки, настройки — показываются как **один живой
фото-экран** с логотипом Aviastan и inline-кнопками. Это даёт
одинаковую ширину карточки/кнопок на каждом шаге. Обычная нижняя
(reply) клавиатура не используется вообще.

Правило обновления экрана (реализовано в `app/bot/screen/manager.py`):

- **Нажатие inline-кнопки** → то же фото-сообщение редактируется на
  месте (`edit_caption` / `edit_reply_markup`), никакого удаления.
- **Текстовый ввод** пользователя (дата, ручной город, цена) → старое
  фото-сообщение удаляется и отправляется новое с обновлённым
  содержимым, чтобы ответ бота оказался в чате **после** сообщения
  пользователя (Telegram не позволяет переместить вниз уже существующее
  сообщение), и в чате не оставалось старых сообщений бота.

Результаты поиска и список подписок дополнительно листаются кнопками
◀️ N/M ▶️ прямо под карточкой — это тот же фото-экран, просто с
несколькими "страницами" в памяти процесса (`_results_cache` /
`_subscriptions_cache` в соответствующих хендлерах, ключ — `chat_id`).

## Навигация: ни один экран не тупик

Каждый экран бота имеет путь назад или отмену:

- Экраны, ожидающие текстовый ввод (дата, диапазон дат, ручной город,
  цена) и экраны ошибок валидации показывают клавиатуру «❌ Отмена»
  (`cancel_only_keyboard()` в `app/bot/keyboards/cities.py`).
- Меню редактирования подписки (например, ввод новой максимальной цены)
  показывает «⬅️ Назад», ведущую обратно к карточке этой подписки, а не
  в главное меню — иначе пользователь теряет контекст.
- Карусели (результаты поиска, подписки), меню настроек и пустые списки
  показывают кнопку «⬅️ В главное меню» (`back_to_menu_button()` /
  `back_to_menu_keyboard()` в `app/bot/keyboards/main.py`), которая
  работает с любого экрана через универсальный хендлер в `start.py`.

**Важное правило при работе с FSM state**: `state.clear()` стирает
`screen_message_id` — если после `state.clear()` вызвать `show_screen`
(например, в конце какого-то флоу), она не найдёт, какое сообщение
удалить, и старый экран останется висеть в чате. Используйте
`clear_state_keep_screen(state)` из `app/bot/screen/manager.py` вместо
прямого `state.clear()` везде, где после сброса состояния показывается
новый экран.

Уведомления (`app/services/notification_service.py`) — единственное
исключение из правила «удалять предыдущее сообщение»: сами уведомления
никогда не удаляются (остаются в чате как история), но перед отправкой
уведомления удаляется текущий открытый системный экран пользователя, если
он был. Под каждым уведомлением есть кнопка «Купить билет» со ссылкой на
именно тот билет, о котором уведомление.

## Админ-команды

`/users` — присылает список всех зарегистрированных пользователей
(`@username`, если есть, иначе имя, иначе «без имени», плюс telegram id).
`/new_users` — присылает только тех, кто не был выгружен предыдущими
вызовами `/new_users`, затем помечает их как выгруженных. Доступ только
у telegram id, перечисленных в `ADMIN_TELEGRAM_IDS` (через запятую) в `.env`.

## Управление подписками

Функция паузы/возобновления подписки убрана полностью — управление
подпиской сводится к «Изменить» (максимальная цена, только прямые/с
пересадкой) и «Удалить». Кнопка «только прямые» в меню редактирования
всегда отражает текущее сохранённое состояние подписки, а не статичный
текст.

## Известные ограничения MVP

- Гибкие даты реализованы через серию точечных запросов в пределах
  диапазона (не более 14 дней зондирования), а не через отдельный
  calendar-эндпоint — при необходимости легко заменить на
  `search_calendar_prices` в `TravelpayoutsProvider._search_flexible`.
- Кэш поиска и кэш карусели — in-memory (в пределах процесса бота). Для
  горизонтального масштабирования на несколько инстансов следует
  подключить Redis (задел уже оставлен в `docker-compose.yml`) и вынести
  туда оба кэша.
- Редактирование существующей подписки (`✏️ Изменить`) поддерживает смену
  максимальной цены и переключение «только прямые»; смена маршрута/дат не
  реализована — для этого проще создать новую подписку.
- Точные названия полей и эндпоинтов Travelpayouts (`client.py`) нужно
  сверить с актуальной документацией на момент запуска в продакшен —
  API может отличаться от версии, использованной при разработке.
- Функционал «Избранное» удалён как дублирующий «Мои подписки».
